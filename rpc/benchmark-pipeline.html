stellar-rpc · O3.1.2 · e2e benchmarking

Benchmarking RPC, end to end.

The goal is to provide developers with one workflow: an ephemeral EC2 box builds the stellar-rpc ref under test, ingests frozen datasets at phase pacing, publishes results to S3, the public results site updates, and Slack delivers the verdict. This document presents the layers we built around stellar-rpc, the journey of one campaign, the methodology behind the numbers, and the PRs that got us here.

01The architecture: four layers, three repos

The pipeline is four loosely coupled layers. Each exposes a narrow interface (CSV files, a TOML config, an S3 bundle) and is caller-agnostic.

system stellar-rpc The system under test: RPC v2 with full-history storage. Every campaign benchmarks one ref of this repo, built from source on the box.
layer 1 bench subcommands bench-ingest cold|hot inside the binary itself. The production ingestion path measured from within, emitting CSVs + invocation.json. #771 → PR #857
layer 2 campaign runner The campaign CLI (stellar-rpc-benchmarks/runner): TOML in → preflight → build the ref → fetch golden packs → run the legs → bundle → publish. #896
layer 3 campaign automation GitHub Actions in stellar-rpc: bench-campaign.yml dispatches, launches, awaits, notifies; bench-reaper.yml guards the fleet. #868 → PR #921
report results site stellar-rpc-benchmarks: ingest.sh converts each bundle into a run JSON; GitHub Pages renders it; targets.json is the single source of phase targets. #871

Around the layers sit two S3 buckets and Slack. stellar-rpc-bench is the data plane — frozen datasets in, result bundles out. stellar-rpc-ci-load-test is the control plane — a tiny result.json the box writes and the workflow polls. The box never holds a GitHub credential; its instance profile can only touch the two buckets.

The validate job turns the form into a runner config: render-campaign-toml.sh checks every enum, range, and ref, expands the phase into a close interval plus three S3 dataset profiles, computes the campaign's time budget, and rejects anything the 21-hour relay chain cannot carry.

  • The ref is resolved on the box, not in CI — any branch, tag, or SHA of stellar-rpc can be benchmarked, including an open PR's head.
  • Campaigns queue, never cancel: the rpc-bench concurrency group serializes runs so two campaigns never share an account's boxes or step on each other's measurements.
  • Three more inputs — hot_num_ledgers, run_name, benchmarks_ref — cover partial runs, naming, and pinning the harness itself.

The trick: poll-relay

A GitHub-hosted job dies at 6 hours; a campaign runs 5 to 17. So no job runs the campaign — the box runs itself, and four chained await windows (5 h 20 m each, ~21 h capacity) merely poll its result.json every 30 seconds, tailing the box log over SSM as they go. A window that ends mid-campaign hands running to the next; a verdict ends the chain. And the budget clock starts after the box launches — runner queue time never eats campaign time.

Three small mechanisms make the loop trustworthy. launch seeds a pending marker before the box exists, so a missing result is always distinguishable from a broken IAM policy. Every result carries a runId of run_id-attempt, so a re-run attempt rejects a stale verdict from its predecessor. And the box, the workflow, and a reaper each hold a termination lever — budget, cleanup job, and a deadline tag — so no failure mode leaves a forgotten box burning money.

The verdict arrives where the team lives

The notify job reads the run-info sidecar, renders a Block Kit message, and posts it. On a pass it also ingests the bundle into the results site — it checks out stellar-rpc-benchmarks and runs ingest.sh --push-main, so the Pages explorer is already serving the run when the Slack message lands. "View results" links straight into it.

When it fails, the box waits for you

A failing verdict does not tear the box down. cleanup sees the failure and leaves the instance up for SSM rescue — results and logs are still on the NVMe — until its own self-termination timer fires. If every in-band ceiling somehow fails, the reaper (bench-reaper.yml, cron twice an hour) terminates any rpc-bench box past its deadline tag and says so out loud.

03Prior art & PR #921: what existed, what we added

None of the Actions layer started from zero. Christian Jonas (cjonas9) built the perf-eval architecture that runs release performance tests on ephemeral EC2, across five merged PRs:

  • #741 — the first EC2 ingestion load test: launch a box, download and verify datasets, run, report.
  • #791 — the generic scatter/gather architecture: ec2-leg.yml, the coordinator, bootstrap-common.sh, and the harness — the S3 result protocol and SSM debug tails that everything since builds on.
  • #830 — the database-backfill leg.
  • #861 — the Go-benchmark leg with benchstat comparison.
  • #855 — the endpoint/blaster leg with chained boxes.

PR #921 (+1,897 lines) stands on that foundation and reshapes it for a different problem: the perf-eval legs are short-lived, release-driven, and report to a PR comment; a benchmark campaign is operator-dispatched, runs up to 17 hours, and reports to the team. Piece by piece:

04The methodology

The numbers mean something because every run answers the same question the same way: the same bytes in, the same pacing, the same targets, the same verdict rule. Four decisions carry that.

1 · Frozen inputs: the golden packs

We generated six synthetic ledger datasets once, with stellar-core apply-load at exact transactions-per-ledger, and froze them into byte-stable "golden packs" on S3 (#867). Three workload profiles, each stressing a different bottleneck — SAC transfers (every transfer mints a fresh, sha256-derived balance entry: relentless state growth), OZ token transfers (contract-token logic), and Soroswap swaps (multi-contract calls, heavy events) — at two load points each, 16–50 GB per pack. A campaign ingests identical bytes every time, so two runs differ only by code and hardware.

2 · The phase matrix

A phase is a network operating point: a block time plus a per-profile load. Picking a phase in the dispatch form pins all of it.

* Targets live in one machine-readable place — docs/targets.json in the benchmarks repo — read by the converter, the viewer, and the Slack verdict alike. The Phase 3 ingest target moved 100 → 80 ms with the read-to-client amendment; the slice accounting is being reworked again in bench#34.

3 · Two legs, two questions

Each campaign runs the ingest bench in two modes per profile. Cold is unpaced: ingest a 10,000-ledger chunk flat out — how fast can this box backfill? Hot is paced at the phase's block time: one ledger per close interval — can this box keep up with the network, and at what p99 commit latency? The hot leg is the one judged against the ingest target; its pace_lag distribution shows how far behind the tip the box ever fell. Both run on the two hardware classes we care about: the published minimum spec (m6id.2xlarge — 8 vCPU, 32 GiB, NVMe) and a headroom box (c6id.8xlarge — 32 vCPU, 64 GiB).

4 · One E2E model, honestly labeled

"End to end" is a defined sum, not a vibe. Each phase's budget decomposes into four slices, and every published figure says which slices are measured and which are still estimates.

SAC is the binding profile at every phase — its fresh-address-per-transfer pattern grows Core's in-memory Soroban state without bound, and the apply-stage tail owns most of every miss. The pipeline did its job twice over: it isolated the bottleneck, and three weeks later the same pipeline validated #902's hot-ingest optimizations — Phase 3 green on the 8x box. Finding the problem and proving the fix ran through the same door.
