04Why compression closed the gap

Core does not hand over a ledger in one piece — it streams it out over roughly 7.5 ms (measured: 7.28 ms median in Run 3). Because the stream is chunked, the network can already send chunks while Core is still producing them. Sending done during those 7.5 ms is free. What hurts is whatever is still left to send after Core finishes — that is the time the client sits waiting.

Uncompressed

One WebSocket is one TCP connection, and EC2 caps a single connection between these hosts at about 5 Gbit/s.

14.48 MiB at 4.96 Gbit/s
= 24.3 ms to send
Only 7.5 ms of that hides behind Core's own emission. About 16.8 ms of sending is left after Core finishes.
Measured: 16.60 ms (controlled p50) — the model matches.
→

Per-chunk zstd

zstd shrinks the SAC-6000 ledgers about 7× before they go on the network.

~2.0 MiB at 4.96 Gbit/s
= ~3.2 ms to send
3.2 ms of sending fits inside the 7.5 ms Core spends emitting. The network keeps up in real time; almost nothing is left at the end.
Measured: 1.56 ms (Real-Core p50).

05What each test answered

Three kinds of test back the numbers: a controlled synthetic stream for repeatable measurements, a real Core process for realism, and control checks that rule out measurement error.

Controlled transport gate

Repeatable tail measurement

1,000 synthetic ledgers, 14.48 MiB each, one every 600 ms, emitted over about 8 ms — the same size and rhythm as the real Core runs.

Purpose: a repeatable setup that produces a stable p99. This is the number the 4 ms gate is judged on.

Real Core reference

Production-shaped source path

Real SAC-6000 LedgerCloseMeta XDR from stellar-core apply-load, read through Core's metadata pipe.

Purpose: check the controlled result against Core's real output pattern — Core emits about 234 smaller chunks per ledger versus 58 in the controlled source.

Controls

Trust checks on the numbers

Re-running the uncompressed legs reproduced earlier results within 0.1 ms, and swapping the sender and receiver hosts showed only 37–50 µs of clock error.

A raw TCP test confirmed the 5 Gbit/s limit is per connection — the hosts' full network capacity is 12.5 Gbit/s.

07Validated & still open

Validated

  • Remote ledger delivery fits the 80 ms PoC budget, including the heaviest recorded ledger shape.
  • Chunk overlap reduced controlled median delivery 1.85× on the same wire.
  • The controlled workload passed the 4 ms gate; the real-Core reference also finished below 4 ms.
  • The client implements the same LedgerStream interface used by RPC v2 ingest.
  • No measured client fell back from a partial live flow to the retention ring in Runs 3–4.

Still outside this PoC

  • Actual integration into stellar-rpc; the repository contains documented wiring, not a merged RPC change.
  • Full RPC ingest p99 and peak RSS with Core removed from the RPC host.
  • Production TLS, authentication, high availability and service ownership.
  • Multi-subscriber scale and recovery beyond the 10,000-ledger retention window.
  • Run 4 caveat: 18 raw compression fallbacks occurred during Core setup; the final Real-Core counter was not captured.
